# 问题归并与系统性识别

> 适用于汇总 `issues[]` 前的综合阶段。目标是减少重复、保留实例证据，并区分局部遗漏与跨页面/跨任务的稳定设计模式。

## 归并条件

同时满足以下条件时，优先合并为一个问题：

1. 违反的是同一设计规律或同一套界面行为。
2. 对用户造成影响的机制相同，而不仅是组件外观相似。
3. `design_objective` 和首选改进方向一致。
4. 合并后仍能清楚表达各实例的位置、状态和证据。

例如多个页面的状态标签使用不同颜色和术语，若都导致用户无法稳定判断对象状态，且需要统一状态语义与组件规则，可作为一个系统性问题。若一个页面是术语歧义，另一个页面是对比度不足，虽然都涉及标签，也应分开。

## 必须分离的情况

- 受影响用户或关键任务不同，导致影响、频率或严重度实质不同。
- 恢复方式、业务风险或设计目标不同。
- 一个是确定问题，另一个只是待验证风险。
- 推荐方向不同，合并后只能写成笼统建议。
- 只有表面组件相似，没有证据证明影响机制相同。

不得为了减少问题数量强行归并，也不得为了显得问题多而拆分相同规律。

## Occurrences

多页面、多任务或 `evaluation_track=visual_system` 的问题必须使用 `occurrences[]`：

```json
{
  "id": "OCC-01",
  "task_ids": ["TASK-01"],
  "surface_ids": ["PAGE-01"],
  "state": "default",
  "observation": "列表页状态标签使用“已完成”，颜色为绿色",
  "evidence_ids": ["EV-01"]
}
```

规则：

- `id` 在当前问题内唯一。
- 至少关联 task 或 surface；引用必须同时存在于问题顶层相应数组。
- `state` 写发生状态；默认静态页面可写 `default`。
- `observation` 只描述该实例的可观察表现，不重复整条问题影响。
- `evidence_ids` 必须是该问题顶层证据的子集。
- 问题顶层的所有 task 和 surface 都必须至少出现在一个 occurrence 中。
- 单页面、单任务的局部问题可以不写 `occurrences[]`。

## 评价轨

- 跨页面视觉或设计系统规律：`evaluation_track=visual_system`，至少关联两个 surface。
- 跨多个关键任务的交互规律：仍使用 `evaluation_track=task`，关联全部受影响 task。
- 同一任务中的单页视觉问题：使用 `visual`，不因组件重复自动升级为 `visual_system`。

## 严重度与范围

实例数量和页面数量不直接决定严重度。按 `severity-rubric.md` 综合任务影响、频率、范围、恢复、业务风险和视觉影响：

- 系统性但只影响局部专业完成度，仍可能是 P2。
- 只出现一次但阻断核心任务，仍可能是 P0。
- 多页面重复只证明范围更广，不能替代用户影响证据。

定级理由应说明最可信的影响和实际范围，不把所有实例影响简单相加。

## 根因边界

只归纳可证实的设计模式原因，例如“状态术语和颜色规则跨页面不一致”。不得推断代码复用、组件负责人、团队协作、历史债务或组织流程等技术/管理根因，除非用户提供可靠证据且明确要求分析。

## 汇总自检

- 是否存在标题、影响和建议几乎相同的重复问题。
- 合并问题是否仍能通过 occurrences 找到每个实例和证据。
- 是否把不同影响机制的相似组件错误合并。
- 是否把单页问题错误标成系统性问题。
- 严重度是否基于用户影响，而非实例数量。
