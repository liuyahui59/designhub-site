# PC B 端双轨评估框架

## 范围

本 Skill 仅正式走查 PC 端 B 端产品：管理后台、业务工作台、数据管理、运营、配置和审批系统。

- 不评价移动端、小程序、App、触屏手势或跨设备任务连续性。
- 输入包含移动端页面时，将其列为范围外，不标 `not_tested`，也不输出移动端结论。
- PC 浏览器缩放、键盘、焦点、对比度和辅助技术仍属于 PC 体验，不能因排除移动端而省略。

## 双轨模型

### 任务体验轨

以 `review_brief.critical_tasks[]` 中的任务契约为单位，检查入口、操作、进行中、结果、异常、恢复和上下文保持。`scope_inventory.tasks[]` 必须复用任务契约的 ID 和名称；每个确定问题关联 `task_ids`，跨任务问题关联全部受影响任务。

### 视觉质量轨

以走查范围内的 PC 页面 / 弹层 / 工作台为 `surface`。每个 surface 必须完成 `visual` 清单；跨页设计系统问题关联多个 `surface_ids`。

视觉问题无需强行关联任务，但必须有页面证据和可解释的质量影响。页面简陋、粗糙、像半成品，若能落到层级、布局、间距、字体、色彩、组件、状态或系统一致性，属于正式问题；纯个人偏好不报。

## 模块路由

每次都启用：

- `core`：`ux-checklist.md`
- `visual`：`visual-checklist.md`
- `accessibility-pc`：`accessibility-pc.md`

满足触发条件时启用：

- `object-lifecycle`：存在创建、编辑、提交、审批、发布、撤回、归档、删除、权限变更，或对象具有两个以上业务状态
- `form-configuration`：关键任务包含创建、编辑、录入、设置或配置，且存在多组信息、字段依赖、重复项、多步骤、长页面、高风险配置或专业控件选型需求；普通搜索框、单字段弹窗和简单确认不启用
- `analytics-dashboard`：范围包含仪表盘、指标卡或数据可视化，且用户需要监控、分析、比较、定位异常或下钻处理；不参与任务判断的少量辅助统计可不启用并说明理由
- `navigation-information-architecture`：产品存在多个业务模块、对象层级、跨页面/跨模块关键任务，或详情包含多种同级视图与子资源；单页工具和不承担跨页任务的简单结构不启用

后续领域模块只在实际存在对应任务时加入；不得为了“覆盖全面”加载与本次任务无关的清单。

## 执行顺序

1. 按 `task-contract.md` 从用户回答建立带独立成功标准的任务契约，并建立同 ID、同名称的 `tasks[]`。
2. 枚举范围内全部 `surfaces[]`。
3. 按 `scope-inventory-completeness.md` 记录清单来源、完整性与已知范围外页面。
4. 选择领域模块并写入 `activated_packs[]`。
5. 按 `pc-environment-validation.md` 记录主要 PC 环境，并用该环境证据覆盖全部 surface。
6. 对每个 surface 完成视觉轨。
7. 按 `cross-page-consistency.md` 横向比较范围页面；合理场景差异不强制统一。
8. 按 `task-state-coverage.md` 为每个 task 建立状态清单并完成流程与适用状态轨。
9. 按 `target-coverage-matrix.md` 形成页面 × 视觉项、任务 × 任务型检查项的完整矩阵。
10. 按 `issue-consolidation.md` 归并重复实例，并汇总跨页面、跨任务的系统性问题。
11. 确定问题写入 `issues[]`；证据不足写入 `validation_backlog[]`。
12. 记录 `positive_patterns[]` 和未覆盖范围。

设计修改后的复查不重做无关范围：按 `follow-up-review.md` 覆盖全部受影响页面与任务，逐项验证原验收标准，并检查视觉、流程、状态和正向模式回归。

## 完成判断

- `complete`：用户指定范围的页面清单为 `confirmed`，主要 PC 环境验证为 `completed` 且证据覆盖全部页面，所有 surface 的视觉状态均为 `completed`，多页面范围的跨页面一致性对比为 `completed`（单页面为 `not_applicable`），且所有关键 task 的状态清单为 `confirmed`、适用状态结果完整、流程状态均为 `completed`。
- `partial`：至少有一条有效观察或确定问题，但页面清单为 `partial`，或仍有 surface / task 为 `partial / blocked / missing`。报告标题必须写“阶段性”。
- `blocked`：没有任何 surface 或 task 取得有效证据，不能形成有效报告。

视觉覆盖率、任务覆盖率和状态覆盖率分别展示，不合并成单一百分比。

## 设计原则与阈值

正式问题必须形成：

> 在具体用户与场景下，当前设计导致可观察的体验或视觉质量影响，证据是实际观察，因此不满足设计原则或项目规范。

其中页面事实与用户影响依据按 `claim-evidence-boundary.md` 分开记录。页面缺陷可由专家走查直接确认；真实耗时、错误率、成功率或业务结果只有在存在用户观察或行为数据时才能作为实证结论。

阈值分三类：

1. **规范性阈值**：WCAG、法律合规、明确品牌规范，可直接作为判断依据，须记录来源与版本。
2. **项目约束**：项目 Design System 或用户确认的业务规范，仅在项目明确采用时直接判定。
3. **经验性阈值**：菜单层级、表格列数、字段数、步骤数、间距倍数，只能作为风险信号，不能直接生成问题或定级。

Fitts 定律用于目标尺寸、距离和精度；Hick-Hyman 定律用于选择数量与复杂度；米勒定律不能作为表格列数、菜单项或字段数上限。示例库只提供诊断思路，不提供默认严重度或通用像素方案。
