# 关键任务契约

> 用途：把用户确认的关键任务与各自成功标准绑定，并让前置调查、实际走查、Coverage 和报告始终引用同一任务。

## 为什么需要任务契约

关键任务和成功标准若分别记录为两个数组，无法证明哪条标准属于哪条任务，也无法防止进入走查后新增、遗漏或改名任务。任务契约以稳定 `id` 建立一对一映射：一个任务对象只描述一条用户任务，并直接包含该任务的成功标准。

## 建立规则

- 不增加前置调查题目；将用户对第 2、4、6 题的回答整理为结构化任务。
- 所有字段都必须能追溯到用户明确回答。无法判断某条标准属于哪个任务时，只追问映射不清的部分，不自行分配。
- 每个任务使用唯一且稳定的 `TASK-01`、`TASK-02` 等 ID；复查沿用原 ID，只有用户确认任务发生实质变化时才新增或替换。
- `name` 使用简短的业务结果名称，不写页面名或控件名。
- `primary_user` 指明执行该任务的主要角色；多个角色执行不同任务时分别填写。
- `start_condition` 说明任务从什么业务条件或入口开始，不展开完整操作步骤。
- `intended_outcome` 说明用户最终要确认的业务结果。
- `success_criteria[]` 只放本任务可观察的完成条件，可包含结果明确、准确性、效率、反馈、数据保持和失败恢复；不强迫不存在的量化指标。

## 结构

```json
{
  "id": "TASK-01",
  "name": "创建订单并确认结果",
  "primary_user": "内部运营人员",
  "start_condition": "从创建订单入口进入下单页",
  "intended_outcome": "订单创建成功且最终结果明确",
  "success_criteria": [
    "提交结果明确",
    "失败后保留输入并可重试"
  ]
}
```

## 与走查任务清单的映射

`review_brief.critical_tasks[]` 是用户确认的任务契约；`scope_inventory.tasks[]` 是同一批任务在本次实际走查中的执行记录。

```json
{
  "id": "TASK-01",
  "name": "创建订单并确认结果",
  "flow_status": "completed",
  "state_inventory": {},
  "evidence_ids": []
}
```

正式走查前必须满足：

1. 两处任务 ID 集合完全一致，不能缺少或额外增加任务。
2. 相同 ID 的 `name` 完全一致。
3. 任务状态、证据、Coverage、问题和复查结果都引用这个 ID。
4. 顶层 `review_brief.success_criteria` 不再使用；成功标准只能存在于所属任务对象中。

映射未通过时不得开始正式走查或生成正式报告。若执行中发现用户确认范围外的新任务，先向用户确认并更新任务契约，再继续检查。

## 质量自检

- 每条任务是否只有一个明确的主要业务结果。
- 起点和目标结果是否能界定任务边界。
- 每条成功标准是否能通过页面状态、交互结果或用户验证进行判断。
- 多条任务的成功标准是否分别归属，未使用一组笼统标准覆盖所有任务。
- 任务名称是否避免“看看页面”“测试按钮”等非业务表达。
