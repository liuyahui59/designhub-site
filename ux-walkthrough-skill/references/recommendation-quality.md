# 改进方案质量方法

> 适用于每个 `issues[]` 确定问题。目标是让建议能指导设计修改和验证，同时避免在证据或约束不足时武断指定界面方案。

## 建议链路

按以下逻辑形成建议，不得从观察直接跳到组件或像素：

```text
当前观察 → 用户影响 → 预期体验 → 设计目标 → 首选方向与理由 → 约束/权衡 → 验收标准
```

- `expected_experience`：描述用户应看到、理解、预测或完成什么，是目标行为而非界面做法。
- `design_objective`：说明本次修改要改善的用户结果。
- `recommendation[]`：给出首选设计方向，可包含必要的结构、组件、文案、状态或交互变化。
- `recommendation_rationale`：说明为什么该方向能解决已证明的问题，以及它依赖哪些已知场景。
- `constraints_tradeoffs[]`：记录效率、防错、密度、理解、权限、风险和上下文之间的关键权衡。P0/P1 或跨页面系统性问题必填；P2 仅在确有权衡时填写。
- `alternatives[]`：只有存在实质不同且都合理的方向时填写，不为凑数量制造备选。
- `acceptance_criteria[]`：描述修改后可观察、可复现的结果，不写“体验更好”“符合规范”。

## 具体程度

建议必须比“优化层级、增强反馈、统一样式、调整布局”更具体，至少说明改动对象、目标状态或目标行为。例如：

```text
差：增强失败反馈。
好：在批量结果区分别展示成功与失败数量；失败项列出对象和原因，并提供仅重试失败项的入口。
```

具体不等于武断：

- 有项目 Design System 或明确规范时，可引用组件、Token、尺寸和版本。
- 没有规范来源时，描述关系、层级、状态与行为，不凭个人偏好指定精确像素、颜色或组件库。
- 简单局部问题给出一个明确方向即可；复杂高风险或系统性问题才补充方案权衡和必要备选。
- 不承诺未知的业务规则、技术能力、数据来源、负责人、工期或开发成本。

## 设计与开发边界

设计建议描述用户体验结果与界面行为，不直接写“修改接口、增加字段、调整数据库、重构组件”。若目标体验可能依赖技术支持，可写为约束或待协同验证，不把未经确认的实现方式当作唯一方案。

## 权衡要求

P0/P1 或 `evaluation_track=visual_system` 至少记录一项真实权衡或约束，例如：

- 高频效率与高风险确认之间如何平衡。
- 信息密度与扫描理解之间如何平衡。
- 保留上下文与界面空间之间如何平衡。
- 权限透明与敏感信息暴露之间如何平衡。

不得写空洞的“兼顾体验与开发成本”。开发成本只有在用户提供可靠信息时才可作为外部约束，且不影响问题严重度。

## 验收标准

每项标准应能通过页面观察、交互复现、截图对比、键盘操作或明确规范进行验证。优先覆盖：

- 用户是否能识别目标信息或操作。
- 关键状态是否出现且含义明确。
- 错误是否可定位、修正和恢复。
- 页面或跨页规则是否一致。
- 关键任务上下文是否保持。

避免只验证“组件已经添加”；验证它是否让用户达到预期体验。

## 输出自检

- 建议是否直接回应当前观察和用户影响。
- 推荐理由是否能解释为什么有效，而非复述建议。
- P0/P1 和系统性问题是否记录了真实约束或权衡。
- 备选方案是否确有实质差异；没有则不写。
- 验收标准是否可观察、可复现，并与预期体验一致。
- 是否越界指定了没有依据的开发实现、像素或组件。
