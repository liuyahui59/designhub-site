# 设计复查方法

> 仅在用户明确要求检查设计修改结果，并提供原走查报告与修改后的实际页面时使用。复查判断最终 UI/UX，不追踪代码提交、开发工单、负责人或实现进度。

## 进入条件

- `review_mode=follow_up`。
- 原报告能够识别原问题、验收标准、用户目标、关键任务和页面范围。
- 修改后的页面可按 `code / url / screenshot` 取得证据。
- 原 `review_brief` 和任务 ID 默认复用；当前对话表明用户、目标、任务、场景、成功标准或约束发生变化时，只补充确认变化项并按 `task-contract.md` 更新结构化记录，不要求重填七项问卷。

缺少原报告时不能声称“已解决”，应请用户补充原报告，或改为一次新的首次走查。

## 复查范围

- `targeted`：覆盖所有待复查问题关联的页面与任务。每个受影响页面重新完成全部视觉质量检查；每个受影响关键任务按 `task-state-coverage.md` 重新确认状态清单，并完成流程、适用状态与恢复路径检查。
- `full`：按首次走查标准重新检查原范围内全部页面与关键任务。
- 修改波及相邻页面、共享组件、全局导航或状态规则时，将受影响范围加入 `scope_inventory`，不能只看修改点截图。
- 本次复查包含两个以上页面时，按 `cross-page-consistency.md` 比较修改后页面及受影响的共享视觉与交互规律。
- 复查继续使用已确认的典型 PC 环境；环境发生变化时只确认变化项，并按 `pc-environment-validation.md` 记录本次实际环境。

复查范围以实际影响为准，不要求无关页面重复走查。`scope_inventory` 只记录本次真正重新检查的页面和任务。

## 原问题状态

每个原问题写入 `follow_up_review.issue_results[]`：

- `resolved`：全部原验收标准均有修改后证据证明通过。
- `partially_resolved`：至少一项通过，且至少一项失败或未能验证；剩余影响仍作为当前问题保留。
- `unresolved`：没有验收标准通过，且至少一项有证据证明失败；当前问题继续保留。
- `cannot_verify`：现有证据无法判断任何验收标准；逐项说明阻塞原因和验证方法，不推断为已解决或未解决。

`partially_resolved / unresolved` 必须通过 `current_issue_id` 指向 `issues[]` 中的当前问题。当前问题按修改后的实际影响重新定级，不机械沿用或降低原 P 级。

验收结果使用：

- `passed`：观察结果满足原验收标准，必须有修改后证据。
- `failed`：观察结果仍不满足，必须有修改后证据。
- `not_verified`：当前无法验证，必须写 `reason` 和 `validation_method`。

## 当前问题与新问题

复查报告的 `issues[]` 只包含当前仍存在的问题：

- `issue_origin=baseline`：原问题仍部分或全部存在，同时记录 `original_issue_id`。
- `issue_origin=new`：修改后新发现的问题，不得冒充原问题的延续。

已解决问题不放入 `issues[]`。新问题按普通确定问题的证据、严重度、建议和验收标准完整记录。

## 回归检查

`follow_up_review.regression_check` 至少覆盖全部复查问题关联的 task / surface，并记录：

- `passed`：未发现修改引入的新确定问题。
- `issues_found`：发现至少一个 `issue_origin=new` 的确定问题。
- `partial`：回归范围存在未完成或阻塞项；正式报告只能为 `partial`。

回归检查包括受影响页面的完整视觉质量、受影响关键任务的流程与状态，以及原报告中相关正向模式是否被破坏。不能只验证“组件已出现”或“需求已开发”。

## 输出自检

- 是否使用修改后的实际页面证据，而非开发说明或口头完成状态。
- 每条原验收标准是否逐项给出结果。
- 部分解决和未解决问题是否继续保留为当前问题。
- 新问题是否与原问题分开，并重新判断严重度。
- 受影响页面是否完成全部视觉检查，受影响任务是否完成流程与状态检查。
- 多页面复查是否完成跨页面一致性对比，并区分合理差异与系统性问题。
- 本次复查的主要 PC 环境证据是否覆盖全部受影响页面。
- 是否检查修改对相邻状态、共享规则和正向模式的回归影响。
