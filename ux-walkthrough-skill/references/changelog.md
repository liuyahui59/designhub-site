# 更新记录

## v3.4.1

- 删除前置调查中与设计体验判断关联度不足的“当前阶段（设计稿 / 开发中 / 已上线）”问题
- 第 1 项仅保留走查对象、范围与发起目的，前置调查仍为 7 项

## v3.4.0

- 结构化报告升级为 `schema_version=7`，新增 `pc_environment_validation`
- 正式视觉走查必须记录与用户回答对应的主要 PC viewport、窗口方式、浏览器缩放和证据
- 主要环境证据覆盖全部范围页面后才能形成完整报告，避免在任意浏览器尺寸下检查后宣称完成
- 用户环境未知时记录实际检查环境和限制，不新增问卷或阻塞前置调查
- 仅在用户明确分屏/窄窗或页面实际出现布局风险时增加额外 PC 环境，不扩展为移动端或固定响应式矩阵

## v3.3.0

- 结构化报告升级为 `schema_version=6`，新增轻量 `cross_page_consistency` 记录
- 多页面范围在逐页视觉检查后必须横向比较页面框架、操作位置、同类组件、状态表达与视觉规律
- 跨页面比较复用各页面证据，不新增问卷、检查项或领域模块，也不要求合理场景差异机械统一
- 完整报告要求比较证据覆盖全部范围页面；单页面范围明确记录 `not_applicable`
- 系统性问题继续使用 `visual_system + occurrences[]`，DOCX 只展示简洁比较结论

## v3.2.0

- 结构化报告升级为 `schema_version=5`，关键任务改为包含主要用户、起点、目标结果和独立成功标准的任务契约
- 移除全局 `review_brief.success_criteria[]`，避免多任务时成功标准无法确定归属
- `scope_inventory.tasks[]` 必须与用户确认的任务契约复用完全一致的 ID 和名称
- 校验器拒绝字符串任务、缺少任务成功标准、任务遗漏/增补和同 ID 改名
- DOCX 在每个任务下直接展示边界与成功标准，保留任务与判断依据的上下文

## v3.1.0

- 结构化报告升级为 `schema_version=4`，每个关键任务新增有依据的 `state_inventory`
- 适用状态逐项记录通过、问题、未验证或阻塞；不适用状态只在有解释价值时记录理由
- 不机械要求固定十状态，允许按实际业务使用自定义状态；标准状态仅作为识别候选
- `flow_status=completed` 要求状态清单为 `confirmed`，且全部适用状态均已形成确定结论
- 校验器强制状态证据关联当前任务，并防止任务在状态缺口存在时形成假完整报告

## v3.0.0

- Coverage 破坏性升级为检查项 × 页面/任务的目标级矩阵，`schema_version` 升为 3
- 每个 `VIS-*` 必须分别覆盖所有范围内页面，每个任务型检查项必须分别覆盖所有关键任务
- 条件领域模块启用后逐任务记录结果，不适用任务必须写明理由
- 同一检查项允许不同目标分别通过、报问题、阻塞或不适用，并强制问题、目标与证据双向一致
- 用户正文继续按问题归并，详细矩阵保留在 JSON 和校验结果中

## v2.9.0

- 新增 `scope-inventory-completeness.md`，为用户指定范围内的页面清单记录来源、完整性和排除边界
- `complete` 报告要求页面清单本身为 `confirmed`，防止遗漏页面后仍形成假完整报告
- 已知范围外页面必须记录原因；权限、环境、动态入口或证据问题不得作为排除理由
- 不新增前置问题，不要求检查整个产品；复查模式只证明本次受影响范围完整

## v2.8.0

- 新增 `claim-evidence-boundary.md`，区分界面事实、专家影响推断、真实用户观察与行为数据
- 每个确定问题增加影响依据、依据理由和影响证据引用
- 专家推断仍可支持正式问题，但不得声称已测得耗时、错误率、成功率或业务转化
- 只有问题是否存在本身依赖用户行为时才进入待验证风险，不强制每次走查进行用户测试

## v2.7.0

- 新增可选 `follow_up` 设计复查模式，复用原报告前提，仅在用户目标、任务或场景变化时补问
- 原问题按已解决、部分解决、未解决、无法验证记录，并逐项验证原验收标准
- 受影响页面重新完成全部视觉检查，受影响任务重新完成流程与状态检查
- 当前问题用 `issue_origin=baseline / new` 区分原问题延续与新回归，不追踪开发工单或实现进度

## v2.6.0

- 新增 `positive-opportunity-method.md`，结构化区分正向模式、增强机会、确定问题与待验证风险
- 正向模式增加具体观察、用户价值、保留指导和证据引用
- 增强机会增加非问题理由、预期价值、适用条件、设计方向和证据引用
- 两类内容均可为空；增强机会禁止 P 级和验证优先级，避免变相进入整改清单

## v2.5.0

- 新增 `issue-consolidation.md`，按设计规律、影响机制和改进方向归并重复问题
- 多页面、多任务或 `visual_system` 问题强制使用 `occurrences[]` 保留 task、surface、state、observation 与 evidence 映射
- `visual_system` 必须至少关联两个页面；实例数量不直接决定严重度
- DOCX 同步展示发生实例，禁止无证据推断技术或组织根因

## v2.4.0

- 新增所有确定问题必读的 `recommendation-quality.md`，建立观察、影响、目标、建议、理由、权衡与验收链路
- 所有确定问题增加 `recommendation_rationale`；P0/P1 与跨页面系统性问题增加 `constraints_tradeoffs[]`
- 备选方案保持可选，避免简单问题为满足格式而制造多方案
- DOCX 同步展示推荐理由、约束权衡与备选方向

## v2.3.0

- 新增 `navigation-information-architecture` 条件模块，覆盖业务结构、导航层级、命名分组、位置感、入口一致性、组件语义、返回上下文与权限入口
- 明确单页工具和不承担跨页任务的简单结构不触发模块
- 明确路由代码、URL 组织、权限接口和菜单配置不属于设计问题，菜单数量与层级深度仅作风险信号

## v2.2.0

- 明确少量不参与用户判断的辅助统计不触发模块，避免无关 checklist 膨胀
- 明确埋点、查询、统计代码、算法与数据仓库不属于设计审查，只有造成可观察体验后果时才上报

## v2.1.0

- 明确普通搜索框、单字段弹窗与简单确认不触发模块，不使用固定字段数量阈值
